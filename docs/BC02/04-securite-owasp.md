## OWASP Top 10 (2021) — mesures Design Guardian

| # | Risque | Mesure Design Guardian | Preuve `fichier:ligne` / migration | Statut |
|---|---|---|---|---|
| A01 | Broken Access Control | RLS Postgres (policies `USING (select auth.uid()) = owner_id` sur `projects`/`assets`/`versions`) **+** garde applicatif cross-tenant côté backend (le backend tourne en `service_role`, qui **contourne** la RLS — la RLS protège donc uniquement les accès directs authentifiés, pas les appels backend) | RLS : `supabase/migrations/010_security_perf_hardening.sql:84-112` (policies `ALTER POLICY ... (select auth.uid())`). Garde applicatif : `backend/src/services/ownership.service.ts:12-30` (`loadOwnedVersion`, commentaire ligne 9-10 : « ce garde applicatif est la SEULE barrière cross-tenant »), utilisé par `branches.controller.ts` (`PUT /versions/:id/status`) et vérification directe `assets.project_id === projectId` dans `checkpoints.controller.ts:26-27`. X-API-Key → `projectId` : `backend/src/middleware/plugin.middleware.ts:11-18`. Test d'intégration prouvant le 403 cross-tenant : `backend/src/tests/branches.controller.test.ts:71-78`. Vue `version_tree` (SECURITY DEFINER, fuite cross-tenant réelle trouvée par `get_advisors`) supprimée : `010_security_perf_hardening.sql:8-16` | **Couvert** |
| A02 | Cryptographic Failures | HTTPS de bout en bout (Railway + Supabase, TLS géré par l'hébergeur — non vérifiable en code) · JWT Supabase validés côté serveur (jamais décodés localement sans vérification) · jeton de liaison de compte (`device_links`) : seul le hash SHA-256 est stocké durablement, le plaintext n'est jamais persisté au-delà d'une lecture unique · secrets (clés API, JWT secret Supabase) chargés depuis l'environnement, jamais commités | JWT : `backend/src/middleware/auth.middleware.ts:22` (`getAnonClient().auth.getUser(token)`, délègue la vérification de signature à Supabase). Hash du jeton de liaison : `backend/src/services/link.service.ts:7-9` (`createHash('sha256')`), token 256 bits (`randomBytes(32)`, ligne 12) ; le plaintext n'est renvoyé qu'une fois puis nullé (`backend/src/controllers/link.controller.ts:57-66`). Secrets en env : `backend/src/config/env.ts:6-28` (schéma Zod), `.gitignore:9-11` (`.env`, `.env.local`, `.env.*.local`) | **Couvert** (HTTPS non prouvable en code — dépend de la config Railway/Supabase, pas auditée ici) |
| A03 | Injection | Aucune requête SQL brute concaténée : tous les accès passent par le query-builder paramétré `@supabase-js` (`.eq()`, `.select()`, `.insert()`, jamais de template string SQL) · validation d'entrée Zod (`zValidator`) sur les routes qui acceptent un body, avec rejet 400 avant tout accès DB | Query-builder paramétré : constaté dans tous les fichiers ouverts (`plugin.middleware.ts`, `link.controller.ts`, `ownership.service.ts`, `checkpoints.controller.ts`, etc.) — aucun `db.raw` / SQL concaténé trouvé. Zod : `zValidator` utilisé dans **7 des 8 controllers** (`grep -c zValidator backend/src/controllers/*.ts` → `projects`, `checkpoints`, `payments`, `link`, `assets`, `notifications`, `branches` ; `auth.controller.ts` n'en a pas car sa seule route est un `GET` sans body). 87 schémas/champs Zod dans `backend/src/types/api.ts` | **Couvert** |
| A04 | Insecure Design | Séparation Service/Controller stricte (logique métier hors des routes HTTP) · monolithe modulaire à 6 domaines (pas de surface d'attaque distribuée non maîtrisée) · rate-limit applicatif sur l'endpoint le plus sensible aux abus (création de code de liaison de compte) · échec fermé (une erreur de validation ou d'appartenance renvoie 4xx avant tout effet de bord) | Rate-limit : `backend/src/controllers/link.controller.ts:16-24` (bucket en mémoire par `projectId`, 30 requêtes/heure, 429 au-delà — ligne 29). Séparation Service/Controller : détaillée et citée dans `docs/BC02/02-prototype-architecture.md` §1.2 | **Couvert pour le flux le plus sensible (`/api/link/start`) — pas de rate-limit générique sur les autres routes (voir Points d'amélioration)** |
| A05 | Security Misconfiguration | CORS restreint par allowlist `CORS_ORIGINS` si configurée · `/metrics` protégé par bearer token, **obligatoire en production** (le démarrage échoue sinon) · moindre privilège Postgres : `REVOKE` des accès `anon`/`authenticated` sur les tables jamais lues en direct par un client | CORS : `backend/src/app.ts:26,29` (`cors({ origin: corsOrigins.length > 0 ? corsOrigins : '*' })`) — **honnête** : par défaut (variable vide) c'est `'*'`, un warning est émis en prod (`backend/src/config/env.ts:50-51`) mais rien ne bloque le démarrage. `/metrics` : garde obligatoire en prod `backend/src/config/env.ts:46-49` (`throw` si `METRICS_TOKEN` absent), vérification du token `backend/src/app.ts:52-57`. REVOKE : `supabase/migrations/011_revoke_anon_table_grants.sql:18-24` (`REVOKE SELECT ON assets, projects, versions FROM anon, authenticated` + `REVOKE SELECT ON profiles FROM anon`) | **Partiel** — CORS ouvert par défaut tant que `CORS_ORIGINS` n'est pas positionné en prod (warning seul, pas de garde bloquante comme pour `METRICS_TOKEN`) |
| A06 | Vulnerable and Outdated Components | Dependabot hebdomadaire sur `backend/`, `plugin/` et les GitHub Actions, minor/patch only (pas d'auto-merge de majors) | `.github/dependabot.yml:1-41` (3 blocs `npm`/`npm`/`github-actions`, `interval: weekly`/`monthly`, `ignore: semver-major`) | **Couvert pour la veille de dépendances** — **pas** d'étape `npm audit` en CI (vérifié : absente de `.github/workflows/ci.yml`, contrairement à une hypothèse initiale) |
| A07 | Identification and Authentication Failures | Authentification déléguée à Supabase Auth (JWT signés, vérification serveur `auth.getUser`) — pas de gestion de mot de passe maison | Auth : `backend/src/middleware/auth.middleware.ts:16-26`. Advisor Supabase « Leaked Password Protection » (HaveIBeenPwned) : **non activable** sur le plan actuel — commentaire explicite dans la migration : `supabase/migrations/011_revoke_anon_table_grants.sql:30` (« 1 WARN leaked_password_protection → bloqué par le plan Supabase free ») | **Partiel** — JWT/Auth déléguée solide ; Leaked Password Protection identifiée par `get_advisors` mais bloquée par le plan Supabase gratuit, non activée |
| A08 | Software and Data Integrity Failures | Webhooks Stripe vérifiés par signature avant tout traitement (aucun événement n'est appliqué sans validation cryptographique) · Quality Gate CI qui bloque le build sous 80 % de couverture | Webhook signé : `backend/src/controllers/payments.controller.ts:53-61` (`stripe.webhooks.constructEvent(rawBody, sig, webhookSecret)`, 400 si signature invalide). Quality Gate : `.github/workflows/ci.yml:31-35` (seuil `coverage.thresholds` de `vitest.config.ts`, la step échoue automatiquement en dessous de 80 %) | **Couvert** |
| A09 | Security Logging and Monitoring Failures | Logging des requêtes HTTP (`hono/logger`) · métriques Prometheus exposées et protégées · endpoints `/health` et `/ping` pour la supervision | `hono/logger` : `backend/src/app.ts:3,28`. Métriques : `backend/src/services/metrics.service.ts:1-5` (`prom-client`, `collectDefaultMetrics`), exposées `backend/src/app.ts:52-60`. `/health` : `app.ts:37-42`. `/ping` : `app.ts:45-49` | **Partiel** — logs applicatifs + métriques réels et déployés ; **centralisation Loki non déployée** (décision documentée dans `docs/BC04-observabilite.md:15-23,49,56`, retenue vs ELK, mais explicitement listée comme reste infra post-oral) ; pas de handler d'erreurs centralisé (`onError`) ni de Sentry (roadmap, cf. axes post-oral BC01) |
| A10 | Server-Side Request Forgery (SSRF) | Aucune route ne fait de requête HTTP serveur vers une URL fournie par l'utilisateur ; les seuls appels sortants vont vers des endpoints fixes de SDKs tiers (OpenAI, Stripe, Resend, Twilio) | Vérifié par recherche exhaustive : `grep -rn "fetch(" backend/src` → **aucune occurrence**. Les intégrations externes utilisent les SDKs officiels (`openai`, `stripe`, `resend`, `twilio`) vers des endpoints fixes, pas une URL passée par le client | **Couvert** (surface d'attaque SSRF absente par construction — pas de fonctionnalité d'import/preview d'URL) |

## Points d'amélioration

Liste honnête des manques identifiés en écrivant ce dossier — aucun n'est présenté comme couvert dans le tableau ci-dessus.

| Manque | Détail | Décision |
|---|---|---|
| En-têtes de sécurité HTTP (CSP, HSTS, X-Frame-Options, X-Content-Type-Options) | Aucun middleware `helmet`-like trouvé dans `backend/src` (recherche `helmet`/`Content-Security-Policy`/`Strict-Transport-Security` : 0 résultat). Risque limité en pratique car l'API n'expose pas de HTML sensible (hors `/api/docs` Swagger UI) et le client principal est un plugin Figma (pas un navigateur affichant du contenu utilisateur), mais reste une lacune de configuration | **Backlog** — ajout d'un middleware d'en-têtes de sécurité (`hono/secure-headers` par ex.) avant commercialisation élargie |
| CORS ouvert par défaut | `CORS_ORIGINS` vide → `'*'`, avec seulement un `console.warn` en prod (`env.ts:50-51`), pas de garde bloquante comme pour `METRICS_TOKEN` | **Backlog** — durcir la garde de démarrage prod pour `CORS_ORIGINS` (même pattern que `METRICS_TOKEN`, `env.ts:46-49`) |
| Rate-limit uniquement sur `/api/link/start` | Les autres routes (checkpoints, branches, notifications) n'ont pas de limite de débit applicative ; elles restent protégées par l'auth (X-API-Key/JWT) et les limites de plan (10 checkpoints/asset en Free) mais pas par un rate-limit générique | **Backlog** — non bloquant pour un plugin mono-projet par clé, à revisiter si l'API s'ouvre à des intégrations tierces |
| `npm audit` absent de la CI | Dependabot couvre la veille (PR automatiques), mais aucune étape ne bloque un build sur une vulnérabilité connue dans les dépendances déjà installées | **Backlog** — ajouter une step `npm audit --audit-level=high` (ou `bun audit`) au job backend de `.github/workflows/ci.yml` |
| Leaked Password Protection non activée | Advisor Supabase identifié, bloqué par le plan gratuit (`011_revoke_anon_table_grants.sql:30`) | **Backlog justifié** — dépend d'un upgrade de plan Supabase, hors budget MVP solo (~30 j-h) ; à activer à la commercialisation |
| Pas de handler d'erreurs centralisé (`onError`) ni de Sentry | Aucune step de capture d'exception centralisée trouvée dans `backend/src/app.ts` ; en cas d'exception non gérée, le comportement dépend du défaut de Hono, non audité ici | **Backlog** — Sentry déjà identifié comme axe post-oral (services de secours + observabilité, `docs/BC01/`) |
| Centralisation des logs (Loki) | Décision technique prise et documentée (`docs/BC04-observabilite.md`), mais Loki n'est pas encore déployé | **Backlog** — reste infra post-oral, explicitement noté comme tel dans BC04 |
